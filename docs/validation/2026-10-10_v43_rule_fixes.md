## v4.3-1. 신규 공시 판정 기준 개선

**문제**
- D2~D10, D5(정정) 규칙이 공시일을 분석 실행일(review_date)과 비교해 "신규"를 판정했음. 오늘 날짜로 분석하면 오늘보다 미래인 공시는 있을 수 없어, 분석 실행일을 오늘로 두는 일반적인 사용 흐름에서는 구조적으로 항상 0건이었음.
- 실측: 이스트에이드의 관리종목지정우려(08-05)·거래정지(08-25, 09-18) 공시가 실제로 수집돼 있고 D7/D8 키워드도 정확히 매칭됐지만, 날짜 비교 때문에 전부 걸러졌음.

**수정**
- `sql/007_views.sql`에 `core.last_review_before(corp_code, review_date)` 함수를 추가해, 기업별 "이번 review_date보다 이전"인 가장 최근 `mart.company_priority` 검토일을 기준으로 신규 공시를 판정하도록 변경.
- 과거 날짜로 비순차 재실행해도 안전하도록 `review_date` 미만으로 명시적으로 제한.
- 직전 검토 이력이 없는 기업(최초 검토)은 `FIRST_REVIEW_LOOKBACK_DAYS`(90일, 분기 보고 주기에 맞춰 팀 결정) 룩백을 적용.
- `aggregate_kpi`의 신규·정정 공시 집계도 동일 기준으로 통일.

**결과**
- 분석 실행일이 아닌 기업별 검토 이력을 기준으로 신규 공시를 탐지하도록 개선.
- 스키마/컬럼 변경 없음 - 순수 SQL 함수 추가라 롤백 시 `DROP FUNCTION` + 커밋 revert만으로 원복 가능.

**검증**
- 테스트 날짜(2026-10-09)에서 이스트에이드가 D7(관리종목지정우려)로 긴급확인 발생 확인.
- 라이브 날짜(2026-10-10) 재실행 후 이스트에이드가 긴급확인으로 정상 표시됨을 Chrome에서 확인.
- pytest 31/31 통과.

## v4.3-2. 영업수익 매핑 및 매출 중복 집계 방지

**문제**
- NAVER와 이스트에이드처럼 매출을 `영업수익`으로 공시하는 기업은 `REVENUE` 계정에 매핑되지 않아 F3(매출 YoY) 규칙이 평가되지 않았음(실측: NAVER REVENUE 0건).
- SK스퀘어처럼 `매출액`과 `영업수익`을 같은 금액으로 중복 공시하는 경우, 두 계정을 단순 합산하면 매출이 2배로 중복 집계되는 문제가 있었음(v4.2-1의 NET_INCOME 중복집계 버그와 같은 종류).

**수정**
- `sql/005_seed_account_mapping.sql`에 `영업수익 → REVENUE` 매핑 추가.
- `scripts/load_core.py`에 `EXCLUSIVE_STD_CODE_PRIORITY` 도입: REVENUE는 `매출액`을 `영업수익`보다 우선해 "동의어 중 하나만" 사용하고 합산하지 않음(순서와 무관하게 항상 우선순위 높은 쪽이 승리).

**검증**
- NAVER: 12.0조 원
- SK스퀘어: 1.9조 원, 중복 집계 없음
- 이스트에이드: 155.8억 원
- 실제 원천 데이터(raw.opendart_financial_calls)와 정확히 일치하는 것을 확인.
- 라이브 재실행 후 NAVER의 F3 매출 YoY +12.1% 평가 확인.
- pytest 31/31 통과.

## v4.3-3. D7/D8 해제 공시 오탐 개선

**문제**
- D7(관리종목·상장적격성·상장폐지)/D8(거래정지·회생절차·부도)이 단순 ILIKE 키워드 매칭이라, "해제"(위험군에서 빠졌다는 좋은 소식)가 포함된 제목도 똑같이 긴급확인으로 매칭됐음 - 방향이 정반대인데 키워드만 보면 구분이 안 됨.
- 실측: 이스트에이드가 정확히 이 경우로 긴급확인에 떴음 - 09-18 "주권매매거래정지해제(액면병합 주권 변경상장)" 공시(절차적 사유로 정지가 풀렸다는 공시)가 D8을 발동시켰고, 정작 진짜 우려 사항인 08-05 관리종목지정우려·08-25 거래정지는 직전 검토일(v4.3-1 기준) 이전이라 "신규"로 안 잡혀 더 묻혔음.

**수정**
- `scripts/run_rules.py`의 D7/D8 WHERE절에 `AND report_nm_clean NOT ILIKE '%해제%'` 추가.

**검증 결과**
- 라이브 날짜 재실행 후 이스트에이드의 실제 위험 신호인 `관리종목지정우려`(08-05)가 D7 사유로 긴급확인에 표시되는 것을 확인.
- 같은 재실행에서 D8도 정상 발동 - 트리거 공시가 "해제" 건(09-18)이 아니라 진짜 거래정지 건(08-25, "주식의 병합·분할 등 전자등록 변경·말소" 사유)으로 바뀐 것을 확인.
- pytest 31/31 통과.

## 후속 개선 사항

- 라이브 날짜(review_date)를 재실행할 때마다 수기 시드 데모 기업(예시B/C)의 `mart.company_priority`/`mart.change_events`가 다른 기업들과 함께 삭제돼, 매번 수동으로 다시 채워야 하는 번거로움이 있음 - 데모 기업이 계속 필요하다면 재시딩을 스크립트화하는 것을 검토.
  - (참고: 예시A는 이번 작업 중 "이 기업 데이터 삭제" API로 의도적으로 제거됨 - 복원 대상 아님.)
- D7/D8의 "해제" 제외 로직이 다루는 실제 공시 문구가 한정적으로만 검증됨(이스트에이드 사례 중심) - 다양한 공시 문구에 대한 회귀 테스트 보강 필요.
- AI 해설(`explain.py`)이 OpenDART "원본 공시서류 다운로드"(document.xml) API의 일시 점검(상태코드 800)으로 인해 다수 기업에서 비어 있음 - 점검 종료(공지: 익일 18시) 후 `python scripts/explain.py --review-date <날짜>`(기업 지정 없이) 재실행 필요. 코드 결함 아님 - 다른 OpenDART 엔드포인트는 정상 동작 확인됨.
- v4.1 검증 문서(`docs/validation/2026-10-10_v41_rule_change.md`) 작성 여부 아직 미결정.
- v4.2-3(예시 기업 다양화)은 사용자가 직접 진행하기로 함.
